# Decisions

Architecture and project decisions for **einring**, recorded from the grilling session on 2026-09-17.
Each entry: decision, alternatives considered, reason. Change a decision by adding a new dated entry, not by rewriting history.

## Naming

- **D01 Project name: `einring`** – "one ring to rule them all"; fits the norse naming of related WIT projects.
- **D02 Android application ID: `de.wit.einring`**, display name **Einring**.
- **D03 Package names: `@einring/app`, `@einring/bff`, `@einring/tokens`.**

## Platform & stack

- **D04 Cross-platform stack: React + Vite + Capacitor** (alternatives: Flutter, React Native/Expo, Kotlin Multiplatform). One web codebase is the WebApp and, wrapped by Capacitor, the Android app; iOS stays possible via `npx cap add ios` on a Mac. Performance is not a driver; existing React and CSS knowledge is.
- **D05 Backend-for-frontend (BFF) from day one**, written in **TypeScript with Fastify** (alternatives: client-only; Express, NestJS, Hono). Service credentials never live on the device; single API for the app; Fastify chosen for typed, schema-validated routes with low boilerplate. The Python `.gitignore` entries stem from a separate Python backend that exposes an API to this app; that backend is not part of this repository.
- **D06 Monorepo with pnpm workspaces**: `apps/app`, `apps/bff`, `packages/tokens` (alternatives: separate repos; npm). pnpm for strict dependency resolution, faster installs and better workspace filtering.
- **D07 Node: pin current LTS (22) via `.nvmrc` and `engines`.**
- **D08 UI components: headless (Radix / React Aria) + own CSS driven by token variables** (alternatives: plain React, Ionic React). Accessible behaviour for free, visuals fully from the design tokens.
- **D09 Frontend libraries: React Router (v8, `react-router` package), TanStack Query v5, react-i18next; headless UI via `react-aria-components`; OIDC via `oidc-client-ts`.**
  - Access/refresh tokens are kept by `oidc-client-ts` in `localStorage` (web and Capacitor WebView). Moving them to a secure-storage plugin on Android is a backlog item.
  - *2026-10-16 amendment*: the UI component layer comes from **biti** (`P:\git\arr\biti`, `src/components/ui/*` — shadcn-style: Tailwind v4 + Radix primitives + cva + lucide), ported near-verbatim into `apps/app/src/components/ui/`; styling resolves through the `@theme inline` block in `global.css`, which maps biti's semantic vars onto `@einring/tokens` variables. `react-aria-components` remains installed for elements biti has no component for yet (Tabs, Popover/Dialog — see the gap list kept with this work). The intended biti theme for einring is **`wuttke`**; its resolved values ship as `apps/bff/themes/wuttke.json`, selectable via `INSTANCE_THEME` (see D37 amendment) — unset, einring's own token values apply.
- **D10 UI languages: German and English from the start** via an i18n layer.
  - *2026-10-16 amendment*: **Russian and French added** — `supportedLanguages` is now `de/en/ru/fr`, every module ships `ru.json`/`fr.json` alongside `de.json`/`en.json`, and plural keys carry all CLDR forms per locale (`_one/_few/_many/_other` for ru). New user-facing strings still go in every supported locale file.
- **D11 Lint/format: Biome** (alternative: ESLint + Prettier). Fall back to ESLint only if a required rule is missing.
- **D12 Git workflow: `main` + short-lived feature branches, conventional commits.**
- **D13 `.gitignore`: one common file for all projects** – keep the Python entries, add Node/Vite/Capacitor/Android; `.agents/` stays ignored while `skills-lock.json` is versioned.
- **D14 Shared WIT guidance is included as the `+wit` submodule** from `https://github.com/ManfredWisniewski/wit-common.git`; it replaces the former `+wit-dev` submodule, which was removed on 2026-10-15.
  - *2026-10-15 amendment*: submodule upstream moved to `ssh://git@git.w1t.org:2222/wit/wit-common.git`.

## Design tokens

- **D15 Tokens live in this repo (`packages/tokens`) as DTCG JSON, edited by hand**, built with **Style Dictionary v4** into CSS custom properties (alternatives: Figma/Tokens Studio export; separate shared token repo). Structured so it can be moved to a shared repo later.
  - *2026-10-15 amendment*: build tool is **Terrazzo** (`@terrazzo/cli` + `@terrazzo/plugin-css`) instead of Style Dictionary — same pipeline as biti, the WIT design-token repository. Reason: one toolchain across WIT token packages; the DTCG resolver format supports theme contexts for future variants. Consequences: sources migrated to strict DTCG values (structured colors/shadows/cubic-bezier, kebab-case ids); semantic aliases now emit as `var(--*)` references; the flat `build/json/tokens.json` output was dropped (no consumer).
- **D16 Token tiers: primitive → semantic**; component tier only when a component needs it. Light and dark are two semantic sets.
- **D17 Theme switching: system preference by default, manual override stored on device**; implemented via `data-theme` on `<html>`.

## Authentication & authorization

- **D18 Identity provider: Authentik via OIDC Authorization Code + PKCE (public client, no client secret).** Nextcloud is already behind Authentik.
- **D19 App ↔ BFF: the app sends the Authentik access token as `Authorization: Bearer`; the BFF validates the JWT statelessly against Authentik's JWKS** (alternative: BFF cookie session). Works identically in browser and Capacitor WebView.
  - *2026-10-16 amendment*: **embedded mode** (`?embedded=nextcloud` on the entry URL, e.g. a Nextcloud External sites iframe) accepts a second credential type. `POST /api/nextcloud/login-flow(+ /poll)` also answer unauthenticated callers, keyed by a random `flow` id instead of a `sub`; completing the flow is itself proof of a Nextcloud identity, so the BFF mints an opaque **einring session token** (sha256-hashed in the `sessions` table, 30-day expiry) and returns it — the app stores it and sends it as `Bearer` like the JWT. Session subs are `nc:<loginName>`; `requireAuth` accepts JWT *or* session via a composite verifier. Disconnect deletes the user's sessions, and the served `index.html` carries `frame-ancestors 'self' <NEXTCLOUD origin>` so only the configured cloud may frame the app. Pending flows expire after 10 minutes.
- **D20 OIDC redirect URIs**: web `https://<host>/auth/callback` and `http://localhost:5173/auth/callback`; Android custom scheme `einring://auth/callback` (alternative: Android App Links – possible later once a public domain exists).
- **D21 One Authentik provider/application for dev and prod for now**; scopes `openid profile email`. Issuer URL and client ID live in gitignored `.env` files with a committed `.env.example`.
- **D22 Nextcloud access: Nextcloud Login Flow v2 per user, yielding an app password** (alternatives: forwarding Authentik bearer tokens to Nextcloud – would require Nextcloud's audience in the token; technical service account – bypasses Nextcloud permissions). Uses the official mechanism; users keep their own Nextcloud permissions.
- **D23 App passwords are stored in the BFF, encrypted at rest, keyed by the Authentik `sub`.** The app never sees Nextcloud credentials; the BFF proxies Nextcloud APIs and hosts the login-flow polling.
- **D24 Nextcloud connection is established lazily**: a "Connect Nextcloud" step on the first Nextcloud-backed screen, not during onboarding. The default Nextcloud login page is sufficient (it forwards to Authentik).
- **D25 Infrastructure prerequisites (reverse proxy / Authentik forward-auth)**:
  - exclude Nextcloud's Login Flow v2 endpoints (`/index.php/login/v2`, `/index.php/login/v2/poll`, `/index.php/login/v2/flow/*`) and API endpoints (`/ocs/*`, `/remote.php/*`, `/index.php/apps/tables/api/*`) from forward-auth interception where required;
  - preserve original `Host`, HTTPS scheme and proxy headers;
  - prefer Nextcloud's own SSO/OIDC integration or Login Flow over injecting Authentik credentials at the proxy layer;
  - the BFF hostname is also excluded from forward-auth (it validates JWTs itself).
  - Testing of file access, photo upload, notifications and WebDAV as recommended by Nextcloud is **out of scope** for einring.

## Data & deployment

- **D26 BFF persistence: SQLite**, app passwords encrypted (AES-256-GCM) with a server-side key from env (alternatives: Postgres, JSON file). Postgres only if the BFF ever runs multi-instance (HA, horizontal scaling, rolling deploys) – not expected for a single-node self-hosted deployment.
  - *2026-09-17 amendment*: driver is Node's built-in **`node:sqlite`** instead of `better-sqlite3`. Reason: `better-sqlite3` ships no prebuilt binary for odd Node versions and needs a C++ toolchain on Windows; `node:sqlite` has zero native dependencies. Consequence: Node >= 22.13 or >= 23.4 required; Node 23.0–23.3 is not supported because `node:sqlite` is unavailable there.
- **D27 Deployment artifact: one Docker image**; the BFF serves the web build (`dist/`) as static files and the API under `/api` (alternatives: separate nginx container). Same-origin, no CORS, and the shape a Nextcloud ExApp expects.
- **D28 Nextcloud integration path**: standalone behind the existing reverse proxy now; cheap integration via Nextcloud "External sites"; long-term intended as a **Nextcloud ExApp (AppAPI)**, which adds the AppAPI handshake to the BFF container.
- **D29 Local dev topology**: Vite dev server `:5173` proxies `/api` → Fastify `:3000`. Android via emulator (`10.0.2.2`) and physical device over LAN (`server.url` from env in `capacitor.config.ts`, never committed).
- **D30 Builds**: local Android builds on the Windows dev machine (Android Studio JDK, `ANDROID_HOME` to be set) **and** GitHub Actions. CI: lint, typecheck, test, web build, debug APK artifact. Release signing later.

## MVP scope

- **D31 First vertical slice: show one fixed Nextcloud Tables table (ID from BFF config) read-only.** Touches auth (Authentik), BFF, Nextcloud Login Flow, tokens and UI. Table browsing, filtering and other services go to the backlog.

## Modules

- **D32 Module framework: a module is a manifest `{ id, requires, app?, bff? }`** — app part bundles route + lazy page + nav item + i18n bundle; bff part registers routes under `/api/<id>` plus an optional env config schema. Frontend-only modules are legal; the BFF part exists only when the module needs API endpoints. Plan: `+wit/development/plans/einring/2026-10-15_plan-module-framework.md`.
- **D33 Enable/disable and module config are deployment-level, env-driven, no admin UI**: `MODULES` lists enabled ids (empty = all enabled); per-module env `MODULE_<ID>_<KEY>` is validated by the module's zod schema at startup only when enabled. `GET /api/modules` reports the enabled set and is the single source of truth for app router/nav. Per-user enablement and a settings UI are backlog.
- **D34 Modules ship bundled in the app**; code-split via lazy import. Downloadable modules are deferred — any future "downloadable" covers large content payloads, not code.
- **D35 Services vs modules**: a service (today: Nextcloud) owns credentials and connection state at BFF level; modules declare `requires: ["nextcloud"]` and the app gates the page on the service's connection status (reusing the Login Flow v2 connect card).

- **D40 Tables module consumes a configured Nextcloud Tables Application (context)** via `MODULE_TABLES_APPLICATION_ID` (the context id from its `/app/<id>` URL): the application's nodes (views + tables) are listed in the app, rows are read and written through view/table-scoped API v1 endpoints (`/api/1/views/{id}/rows`, `PUT /api/1/rows/{id}`, `deleteRowByView`), so filters, sorting, column visibility and sharing rights stay configured in Nextcloud — einring is the mobile client, not the authority. The context listing is the sole OCS v2 call (`/api/2/contexts/{id}`; v1 has no contexts). `MODULE_TABLES_TABLE_ID` and `GET /api/tables/current` are removed — this supersedes D31's fixed-table MVP. CSV import into Tables is out of scope for this module (csv-manager stays the einring-side import path). Cells keep native types: `selection`+`check` renders as a checkbox (the "done" pattern), `number` numeric, `text` inline-editable, `selection` as dropdown, `datetime`/`usergroup` read-only in v1. Plan: `+wit/development/plans/einring/2026-10-16_plan-tables-manager.md`.

- **D41 EinChat + connector modules**: modules may expose `chatTools` — `{name, description, JSON-schema params, call(args, sub)}` — which the `einchat` module aggregates over all enabled modules; `POST /api/einchat/message` drives an OpenAI tool-call loop (max 5 iterations) over the client-sent message history (stateless — same as D39). LLM config moves to **global** `LLM_URL`/`LLM_API_KEY`/`LLM_CHAT_MODEL`/`LLM_EMBED_MODEL`/`LLM_TOP_K`/`LLM_TIMEOUT_S` consumed by any module via `ctx.llm`; `MODULE_WIKI_LLM_*` is removed. Connector modules (first: `yamtrack`) are thin BFF+config surfaces for external services; per-user credentials live in a generic `service_credentials` table (`secrets`-sealed per sub) — one external account **per einring user** (owner decision), modules without a stored credential answer their tool with `{error:"not_connected"}`. Plan: `+wit/development/plans/einring/2026-10-16_plan-einchat.md`.
  - *2026-10-16 amendment*: **EinChat is the conversational front-end to every einring module** — connectors are not limited to external services; every module is expected to expose a `chatTools` connector over time. The connectable set is exactly the enabled set (D33): modules disabled via `MODULES` contribute no tools and never appear in the UI. Each connection is toggled per user in the EinChat **Data connections** settings (`GET`/`PUT /api/einchat/tools`, persisted in `module_settings` per `sub`); a disabled connection's tools are never sent to the model.

- **D36 Wiki module mirrors Collectives via WebDAV**: the BFF syncs `.md` files under `remote.php/dav/files/<user>/Collectives/` into SQLite (`wiki_pages`, etags for change detection, pruning of deleted pages) and serves tree/page/search endpoints. Read-only mirror — no write-back. Chosen over the Collectives REST API because the file tree is the durable contract (localized collective names, custom folder layouts) and DAV needs no Collectives API version assumptions. Markdown is rendered client-side with marked + DOMPurify.
- **D37 Whitelabel deployments via BFF runtime env**: a single image can be deployed under a different brand. `INSTANCE_NAME`, `INSTANCE_TAGLINE` (unset = app default, empty = hidden) and `INSTANCE_CSS_VARS` (JSON map of `--var:value` overrides, injected as a `:root{}` style block into the served `index.html`) are exposed to the app via the public `GET /api/config`. Combined with `MODULES` (D33), one image serves both the default "Einring" deployment and restricted whitelabel instances without a rebuild. Chosen over build-time (`VITE_*`) branding because per-instance builds would defeat the shared CI image. Out of scope for now: the Android app identity (`de.wit.einring` bundle id, app icon) — whitelabeled mobile builds would need their own Capacitor package.
  - *2026-10-16 amendment*: `GET /api/config` now also serves `authentik: {issuer, clientId}` from `AUTHENTIK_ISSUER`/`AUTHENTIK_CLIENT_ID`. The SPA builds its OIDC `UserManager` lazily, only after the config fetch resolves, and prefers the runtime values — the baked `VITE_AUTHENTIK_*` args become the fallback for builds without a BFF (e.g. offline dev). Same reason as the rest of D37: the OIDC issuer/client-id are public values the browser sees anyway, and per-instance baking defeated the shared image.
  - *2026-10-16 amendment*: `INSTANCE_THEME` selects a **named biti theme** at deploy time. Themes are JSON files shipped in `apps/bff/themes/<name>.json`, each holding `light`/`dark` maps of *einring's* CSS variables resolved from the biti theme's tokens (first: `wuttke`). The BFF loads and validates the file at startup (unknown name or malformed map fails fast), injects `:root{}` + `[data-theme="dark"]{}` blocks into `index.html`, and exposes the maps on `GET /api/config` so the dev server applies them too. `INSTANCE_CSS_VARS` keeps working and wins over theme values. New themes = translate the biti theme's tokens into a new `themes/<name>.json` — no component changes.
- **D38 CSV Manager module stores user CSV files in the BFF's SQLite** (`csv_files` + `csv_rows`, scoped by `sub`; cells/headers as JSON, cells positional arrays aligned to the header row). Uploads are JSON `{name, csv}` bodies — no multipart; the server parses (delimiter auto-detected) so parsing is tested once, not per client. Each row carries an einring-level `done` flag outside the CSV cells. The module has no `requires` — it works without Nextcloud. Chosen over Nextcloud Files storage (would add a service dependency and conflict semantics the feature doesn't need) and over client-side storage (data must survive device changes; D26 already commits the BFF to SQLite).
- **D39 Wiki LLM Q&A: retrieval-augmented generation over the wiki mirror via an OpenAI-compatible `/v1` provider.** Mirrored pages are chunked heading-aware into a `wiki_chunks` table (scoped by `sub`, embeddings as `Float32` blobs, etag-based re-index); `POST /api/wiki/ask` embeds the question, cosine-ranks chunks in JS (no vector extension — no native deps, corpus is mirror-sized) and prompts the chat model with the top-k chunks; the answer carries source page paths. Provider is `MODULE_WIKI_LLM_URL` + `MODULE_WIKI_LLM_API_KEY` (default `https://openrouter.ai/api/v1`, key never leaves the BFF — same rule as Nextcloud credentials); unset = feature disabled (424, hidden UI). One `/v1` code path covers OpenRouter *and* local alternatives (llama-server, LM Studio, Ollama `/v1`) — switching is env-only. Chosen over in-process inference (`node-llama-cpp` — reopens the D26 native-build problem; model artifacts in the image) and over on-device inference (native bindings in the Capacitor app, multi-GB model download, and the RAG index would have to sync to the phone since the mirror lives in the BFF). With OpenRouter the retrieved chunks + question leave the deployment — accepted by the owner, documented in DEPLOYMENT.md. v1 is stateless single-turn (no conversation memory) and non-streaming (full answer per request); SSE streaming and multi-turn sessions are backlog. Plan: `+wit/development/plans/einring/2026-10-16_plan-wiki-llm.md`.
- **D42 EinHub collects notifications from modules via a `notifications` capability.** Every `BffModule` may expose `notifications(ctx, config): {poll(sub): Promise<NotificationItem[]>}` alongside `chatTools` (same opt-in pattern as D41) — `poll` returns the module's recent upstream items `{sourceId, title, body?, at?}` and `[]` when unconnected or failing. The `einhub` module collects these sources over the enabled set (D33), diffs items by `UNIQUE(sub, module, source_id)` into a `notifications` table, and serves them per user — refresh is lazy (on `GET /api/einhub/notifications`, throttled per `sub` via `MODULE_EINHUB_REFRESH_SECONDS`) rather than a background poller, so upstreams are only queried while a user actually has the app open. The first poll of a module seeds existing items as read — a notification hub must alert on *new* events, not the whole history. einhub sits first in both module arrays, which makes it the nav's first entry and the app's index route (the router picks the first nav module).
- **D43 GitLab connector uses a personal access token and the Todos API as its notification surface.** GitLab has no pull API for its UI notifications (they are email/web UI state); the Todos API (`GET /api/v4/todos?state=pending`) is the canonical API-side "needs attention" list — assignments, mentions, review requests, failed pipelines. The module seals a PAT per `sub` via the shared apiKey connector routes (verify through `GET /api/v4/user`) and feeds pending todos into EinHub (D42) with `sourceId` = todo id. `MODULE_GITLAB_URL` may preset a self-hosted instance — the WIT GitLab is the expected default.
- **D44 GitHub connector uses a personal access token and the Notifications API.** Unlike GitLab, GitHub exposes real pull notifications: `GET <api>/notifications` threads (`reason`, `subject`, `unread`). The module seals a PAT per `sub` via the shared apiKey connector routes (verify through `GET /user`) and feeds threads into EinHub (D42) with `sourceId` = thread id. The connector `url` is the *instance web URL* and the BFF derives the REST base — `api.github.com` for github.com, `<host>/api/v3` for GHES — so the connect form stays one field for both.
